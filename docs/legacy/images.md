Digitized Images are currently managed through a combination of products often called the repository, repo, or image repo.
There is no staff-facing frontend to view or manage the contents of the repo.

## Ingest Requirements

Digitized image ingest requirements are derived from the requirements of the ImageProcessor ingest process.

1. File names must start with an ID number generated by MMS.
2. File names must end with `U.tif` or `S.tif`.
3. Every ID number should have both a `U` and `S` version.
4. All files must be TIFFs with uncompressed image encodings.

## Architecture Components to Migrate

The primary components of the digitized image infrastructure that would be replaced by Preservica are an ingest process called ImageProcessor, a file registration database called Filestore, and a descriptive and right metadata system called MMS.
Other components take the outputs of these processes to provide access.

## Files and Metadata to Migrate

### Object Modeling Differences

In NYPL's Preservica implementation, the content files of a digitized object are considered a single Information Object.
Relationships between derivatives are managed within that object.

In Filestore, image files are grouped with their derivaties by an ID.
Within MMS, these groups are called a capture, and captures are associated with an item, which is defined by a description and a rights profile.
MMS items may represent all or portions of one or more source objects.

Migrating the digitized images into Preservica will require determining:

* how to map captures to source items
* how to model those captures from source objects that were partially digitized

### File Set Differences

The current ingest process creates roughly 6 to 9 derivative files per image.
With the implementation of IIIF at NYPL, these derivative files will not be necessary and can be discarded.

IIIF performance can be improved by storing image data with lossless or visually lossless image codecs.
It may be useful to transcode the production images or create new access representations as part of the migration.

### Non-Collection Files

Non-collection files, such as exhibition photography, are occasionally run through Image Processor.
These files probably should not be migrated to Preservica.

### Managing File Versions

If something is digitized again, the resulting files are assigned the same ID number for ingest.
ImageProcessor than marks the previous version of image as inactive.

Migrating these versions will require PAX packages to create Generations of each representation.

When a file is incorrectly give the ID of an existing image.
Then, it and its derivatives, will be registered as the latest version of that image.
Because there is no deletion functionality, the solution to these mistakes is to re-ingest the previous/correct version.

These situations can be identified and removed via checksum comparisons.

### Non-image files

Occasionally, projects deliver additional files such as OCR, PDF, and XML.
Alternative ingest methods have added these files to the Filestore, but they are not viewable or retrievable via standard methods.
They also are not related to the item records in MMS.

Locating and modeling these files will require an optional component for the standard package structure.
